# Decisions

Since nanocode-ts e489230 (2026-10-28) the package exports namespaces, so the names below map as `createNanocode` to `App.create`, `aiGateway(ai, id, tier, ms)` to `Gateway.create(ai, { id, serviceTier, firstByteMs })`, `relay` to `Relay.route(request, { namespace })`, `client` to `Limit.client`, `bearerToken` to `Remote.bearerToken` (`nanocode-ts`), `createWallets` to `Wallets.create`, `MachinesEnv` to `Env.Env` (`nanocode-ts/machines/cloudflare`), `visitor` and `VISITOR` to `Account.visitor` and `Account.visitorHeader` (`nanocode-ts/machines/server`), and in the UI `createConfig` to `Config.create`, `modelItems`/`thinkingItems` to `Pickers.models`/`Pickers.thinking`, `cloudflare(...)` to `Transport.create(...)` and `Keyring.keyring` to `Keyring.create`. `worker/index.ts` also passes `mcp.store: env => Listings.store(env.MCP_LISTINGS)`, one `McpListings` Durable Object (migration `v7`) that keeps the Tempo MCP servers' `initialize` and `tools/list` answers for every session: new sessions land in other isolates, whose in-memory listing cache was empty, so on 2026-10-28 a new session's first turn spent 3.1-3.2 s opening its runtime without a warm (two sessions, before) and 60-171 ms after the first session of the deployment had stored the listings (that first one 4.3 s). `createNanocode(options)` from `nanocode-ts/cloudflare` (nanocode-ts's `src/cloudflare/App.ts`), which returns the `AgentSession` Durable Object class and the Worker `fetch` handler. The library defines interfaces and ships no adapters. `options.authenticate(request, env)` returns the caller's account ID, `{account, read_only: true}` for a caller that may only read, or `null`; each account's sessions live in separate objects named by `[account, session]`. A read-only caller gets 403 for every session request other than GET and for attaching a hand, and its session socket streams events but answers `turn` and `cancel` with 403 and `warm` with `warmed: false`. A principal may also carry `grant`, a JSON value the host defines, and `expires_at`, its credential's expiry in milliseconds since the epoch. The session keeps both with each turn the caller submits, with its session socket's registration and with its hand's `hand_sockets` row, and passes the grant of the turn it is running to host tool calls. Sockets and event streams outlive the request that authenticated them, so the session checks the caller before it admits each session socket message, before it delivers events to a watcher, before each read of an event stream and before each frame it sends to a hand or accepts from one, in arrival order: past `expires_at`, or when the optional `options.active(account, grant, env)` returns false or throws, it sends the session socket `{"type":"error","error":"access token expired or revoked"}` and closes it with 1008, ends the event stream, or disposes the hand connection, which fails the cell that was being sent as not dispatched and detaches the hand. Event delivery runs the `active` check in the background, so a watcher can receive the batch published while its first failing check runs; hosts that cache the answer bound how long a revocation takes beyond that. The error frame arrives at once, but a close issued outside the socket's own message handler reached the client about 10 s later in local workerd and 42 s later in production, while one issued from its message handler arrived within 319 ms in production. `options.egress(env)` returns anything with `fetch(request)` that answers the egress contract: `POST /model` with the provider body and the `x-nanocode-model` JSON header `{provider, authority, endpoint, headers, subscription}`, `GET /socket` upgrades for Codex Responses sockets with `x-nanocode-socket`, `GET /remote` upgrades to a configured execution host with `x-nanocode-authority`, and `GET /metrics`. A service binding to a separate Worker satisfies it directly. `MODEL_AUTH` tells the agent whether both providers use subscription or API-key wire compatibility; the optional `options.subscription(account, env, provider)` decides it per account and provider instead, for an egress that holds each account's own credentials. The optional `options.recordSession(account, name, env)` lets a host keep an index of each account's sessions: a session object calls it before handling its first request and, once it returns true, writes a `recorded` metadata row and never calls it again, so sessions created earlier are indexed on their next request; false means the account no longer exists, and the session deletes its storage and answers 403. The returned `deleteSession(account, name, env)` calls the session object's internal delete route, which the public routes cannot reach: it closes the session's hand and watcher sockets, disposes its runtimes and their model sockets, deletes its alarm and all of its storage, and the instance answers 410 until it is evicted and opens no WASM instance meanwhile, since the recovery note of a turn that was running when the session was deleted recreated the turn log's tables in the emptied storage. Claude subscription sessions use Claude Code's wire compatibility. Codex subscription sessions use the ChatGPT Responses WebSocket with `OpenAiAuth::host_managed_chatgpt()`, and Codex API-key sessions use the public Responses API at `https://api.openai.com/v1` over HTTPS with `OpenAiAuth::gateway_managed()` and the SDK's default of store: false, so every model call replays the full history and OpenAI retains nothing; Codex subscription sessions also keep store: false, as the ChatGPT backend requires, and continue responses on their socket. The SDK can store and continue API-key responses with `.store(true)`, but measured through AI Gateway storing a response delayed its first byte by about 0.2 s while continuing one saved only request bytes, so the Worker leaves it off. The egress must agree, and a resident runtime reopens when a later turn's mode differs. The library makes no outbound requests itself and holds no credentials.

The default deployment in `worker/` uses Cloudflare AI Gateway through the `AI` binding. `aiGateway` from `nanocode-ts/cloudflare` implements the egress contract through the binding: Claude Messages requests go to `env.AI.run("anthropic/<model>", body, { gateway: { id: AI_GATEWAY_ID }, returnRawResponse: true })` with only the `accept`, `content-type`, `anthropic-version` and `anthropic-beta` headers, and Codex Responses requests go to `env.AI.gateway(AI_GATEWAY_ID).run()` at its OpenAI provider's `responses` endpoint with only `accept` and `content-type`, and with `service_tier` set to `OPENAI_SERVICE_TIER` when it is set, as `npm run deploy:demo` sets it to `priority`. The gateway supplies the provider key from the BYOK key stored under its `default` alias or bills the account's Unified Billing credits, and the response streams back with provider and `cf-aig-*` headers. Claude goes through `env.AI.run` because on 2026-10-21 the gateway's Anthropic passthrough (`gateway().run()` with provider `anthropic`) sent no key to Anthropic on a gateway without a BYOK key, which answered `401 x-api-key header is required`, even in Tempo Development Resources with $499.95 of credits, while `env.AI.run` and the REST `/ai/v1/messages` endpoint billed the credits and streamed Messages events with tools, `cache_control` and `anthropic-beta` intact. That path names models as Cloudflare's catalog does, `anthropic/claude-haiku-5.5` for Anthropic's `claude-haiku-5-5`, and answers `not_found_error` for `anthropic/claude-haiku-5-5`, so the egress rewrites the request's model from Anthropic's form to the catalog's (`-5-5` to `-5.5`), and responses still name Anthropic's model. The local runtime's `AI` shim implements both calls and reverses that rename before the mock provider sees the request. Binding requests are pre-authenticated, so the Worker holds no provider key or gateway token. The route parses each body anyway to pass it as the binding's `query`, so it answers with an `x-nanocode-model-diagnostic` of the request's body bytes, input item count and whether it continued a previous response, which session metrics list in `model_diagnostics`. The gateway route carries both providers over HTTPS only: `/socket` answers 426, so Codex keeps to HTTPS, and Codex subscriptions and execution hosts need an egress that serves them, such as the platform's; `/remote` answers 501, so a turn naming an executor fails at once with that answer as its error. `worker/index.ts` authenticates one account by comparing the bearer token's SHA-256 with the `ACCESS_TOKEN_SHA256` variable; an empty value rejects every request. Against an account's `default` gateway with no key in the Worker, a deployed Claude turn completed through the binding in 3.4 s of run time. On 2026-10-19 the deployed default Worker completed a Codex turn through the gateway's OpenAI provider in 6.8 s from submission on a new session and 2.1 s on the next turn, and a Claude turn in 5.0 s. A deployed Codex turn of three sequential `list_agents` calls and a reply sends 36.8–43.1 KB on every call, 158 KB and 169 KB per turn; with store: true (SDK b651367, since reverted) it sent 2.1 KB on each continued call, but the median model-call time rose from 1.56 s to 2.15 s. Turns are queued durably in the SDK's turn inbox and deduplicated by `request_id`; reusing an ID with different input returns 409. SDK ownership fences, revision checks, immutable records, model receipts, tool receipts, subagent journals, and checkpoints use the persistent store. No memory store is used for agent state.

Alarms drive work independently of client connections. A watchdog alarm is persisted before execution, using `RECOVERY_DELAY_MS` as an operator recovery policy. Completed requests return saved results. Interrupted model calls may repeat; dispatched tools retain the SDK's uncertain-outcome handling. The Worker does not promise exactly-once model billing or external side effects. Concurrent sessions use independent Durable Objects. Each session executes queued root turns serially, while SDK subagents can run concurrently. Durable background markers keep alarms armed after root requests finish until the SDK task tree, continuation turns, journal writes, and detached remote execution are quiescent. Resume pending SDK operations in accepted order before later requests. Cancellation must settle in the SDK before the queue reports it complete, except for a turn whose runtime cannot open, which finishes cancelled at once and which the SDK cancels on admission when the runtime next opens, and a turn whose cancellation was requested when its drive fails, which finishes cancelled the same way: a turn whose drive fails every time, such as one whose events could not be logged before the SDK replaced oversized ones, otherwise recovered every `RECOVERY_DELAY_MS` forever while every later turn stayed queued, and cancelling it changed nothing. The SDK reserves the `subagent-completion:` request-ID prefix for its own continuation turns, and admission answers 400 for it.

A turn waits instead of running while its execution host is unavailable: when the runtime for it cannot open, or it names a `hand` that is not attached, the pump classifies the failure from its signal and does not guess. Permanent failures finish the turn as failed with `error` and `kind` in its result, so a client's wait ends: a non-101 answer from egress `/remote` with a 4xx status other than 408 and 429, which is `unauthorized` for 401 and 403 and `rejected` otherwise, a 501 (`rejected`), and a runtime configuration the SDK refuses while building it (`configuration`, which `init` answers as a rejection). Everything else is transient and keeps the turn queued, or running for a recovered turn, retrying after `RECOVERY_DELAY_MS` × 2^(attempts − 1) up to `RECOVERY_BACKOFF_MS` (3600000, one hour, chosen without measurement as the longest wait between retries): a 5xx other than 501, 408 or 429 from `/remote` (`unavailable`), no HTTP answer, the `REMOTE_TIMEOUT_MS` connection deadline or a socket closed before its catalog (`unreachable`), an absent hand (`detached`) and any other open failure (`runtime`). The SDK session log's `retry` keeps the message, kind, attempt count and next retry time on the turn, its status report shows them as `error`, `kind`, `attempts` and `retry_at`, and its event stream gets a `retrying` event when the error first appears or changes, not on every retry. A hand attaching starts a turn waiting for it at once, so a turn waiting for a hand stops its timer once one retry waited the whole hour, and keeps its last `retry_at`. Cancelling a waiting turn finishes it, and session metrics report the pending alarm as `alarm_at`, `null` once nothing is left to retry. The pump commits the background marker only once a queued turn's runtime has opened, so a turn whose runtime never opened leaves nothing retrying after it fails or is cancelled; with no unfinished turn, a permanent failure drops an existing marker and a transient one keeps retrying for the SDK's background work.

Cloudflare chooses physical Durable Object placement. Agent execution and checkpoint storage are co-located by construction; this does not pin all objects to an exact Cloudflare colo. SQLite access stays inside each session, including the full SDK subagent tree. Reuse the resident WASM instance and SDK session across turns. Status, a queued turn's cancellation and event history read through the SDK's session log on a WASM instance without opening the SDK session (instantiating the compiled module took 0.3 ms locally), and opening the session later reuses that instance. Root turns are serial, while SDK children can run concurrently.

The default tool collection omits local machine tools and enables SDK delegation. Shell, filesystem, desktop, and remote Code Mode execution require a separately configured execution host; this Worker does not create a machine environment: hands dial in, and an egress may connect configured execution hosts at `/remote`. Use the SDK RemoteFrame/RemoteOperation protocol for that host, with orchestration and tool receipts remaining in the brain. A machine executor's unrestricted network access is governed by that host; the Worker cannot enforce a proxy for an independently configured machine.

Recovery delay, event page size, the event tail's byte bound, event coalescing, the event-stream keepalive interval (`EVENT_STREAM_KEEPALIVE_MS`), the model-socket linger, the runtime memory budget, and execution-host frame and timeout policies are explicit Wrangler variables.

The Worker has no Rust of its own and builds none: the bundle imports the package's compiled module as `nanocode-ts/nanocode_wasm.wasm`. Run the package's checks in nanocodexyz/nanocode-ts and SDK checks from `../nanocodex` with `cargo check --locked --lib` and `cargo check --locked --lib --target wasm32-unknown-unknown`. `package-lock.json` pins the Worker's npm dependencies, nanocode-ts's commit included.

The package's `AgentRuntime`, `EventHub` and `RemoteExecutor`, its bridge ABI and command table are documented in nanocode-ts's `AGENTS.md`; protocol, turn and event logic belongs in the SDK and host-agnostic glue in the package. The session Durable Object supplies the package's host interfaces. nanocode-ts's `src/cloudflare/internal/Checkpoints.ts` is its `SqlHost`, the package's `Sql.create` (`nanocode-ts/cloudflare`) with the Worker's metrics as its observer: it runs each `store` or `log` operation's statements in one `transactionSync` and answers with each statement's rows; metrics count the two separately (`checkpoints` and `log`). The SDK owns the `states`, `owners`, `records`, `turns` and `events` tables, their fencing, revisions and record immutability, turn states and event sequence; the Worker only reads their row counts for metrics. Model requests go to egress `/model`; Codex Responses sockets upgrade through egress `/socket`, and the session accepts the WebSocket and hands it to the package with the egress's `x-nanocode-stream-idle-ms` deadline. nanocode-ts's `src/cloudflare/internal/Executor.ts` dials a configured execution host through egress `/remote` with `Remote.connect` and throws `Executor.RejectedError` with the status of a refused upgrade, and hands attach through the hibernation API with `RemoteExecutor.accept` and `restore`, so frames stay opaque, `REMOTE_MAX_FRAME_BYTES` is enforced and each hand's catalog text is kept for hibernation. The package flags each batch that holds a request the SDK's `RemoteFrame::dispatches` marks as starting work, so the session refuses that batch once the turn's cancellation is requested without decoding frames. Two commands run on the scope's WASM instance without opening the SDK session: `catalog` reads the name a hand advertises in its catalog, and `admit` asks the SDK's `admit_prompt` whether a turn may enter the inbox, so admission takes the reserved request-ID prefix and the provider rule from the SDK. Each logged event batch reaches the session's `published` callback with `host_timing`, the session answers a finished turn's timings through `finishing`, and the SDK selects each turn's hand with `select_prompt_hand`; turn states, the queue, cancellation before and during a turn, resumption in accepted order, event attribution and quiescence live in the SDK. Egress injects provider credentials, so Claude clients send no auth headers and Codex uses `OpenAiAuth::host_managed_chatgpt()`.

Hosts add their own tools through `createNanocode({ tools: { definitions, call } })`. `createNanocode({ streamToolInput: true })`, which the default deployment sets, opens sessions with nanocode-ts's `stream_tool_input`, so the event stream also carries each tool call's input while the model writes it, and the page's shared `Transcript` shows the call, such as a `charge` with its memo, as a live line until it starts. Each definition's `name`, `description` and JSON Schema `parameters` reach the runtime when it opens, and the package registers them as the SDK's `FunctionTool`s beside the SDK's own tools, offered directly or inside Code Mode scripts. A call crosses the bridge as the `tool_call` host operation; the session Durable Object takes the durability wait it takes before any external effect, refuses it once the turn's cancellation is requested, and awaits `call({ authority, name, input, grant }, env, signal)`, whose result becomes the tool output and whose thrown error a tool error. `grant` is the grant of the turn the session is running, read from its `background:<scope>` row, which holds that turn's descriptor until the runtime settles, so subagents and other background work that continue after a turn run with the grant of the latest turn the session started, and turns submitted before grants existed carry none. The SDK keeps the call's receipt like any tool's, so an interrupted call reports an unknown outcome instead of running again, and session metrics count `host_tool_calls`. Whatever the host keeps out of the result never enters WASM memory, checkpoints or events; the platform serves its credential tools this way so injected secrets stay in its egress.

Deploy from this directory:

1. Run `npx wrangler login`, or provide `CLOUDFLARE_API_TOKEN` through your secret manager.
2. In AI Gateway, use the `default` gateway or create one and set `AI_GATEWAY_ID`. Add an Anthropic key under Provider Keys with the `default` alias, or load Unified Billing credits; the AI binding consults only the `default` alias.
3. Generate an access token, keep it in your secret manager, and deploy with its digest: `npx wrangler deploy --var ACCESS_TOKEN_SHA256:$(printf %s "$TOKEN" | shasum -a 256 | cut -d' ' -f1)`. Clients and hands send the token itself as `Authorization: Bearer`.
4. `npm run dry-run` bundles the Worker and its `public/` assets into `output/deploy` for review. Wrangler adds files to an existing output directory without removing old ones, so bundle into a fresh directory, such as `--outdir output/deploy-ts`, when `output/deploy` holds a bundle from before the nanocode-ts move, and point `NANOCODE_BUNDLE_PATH` at it.

Submit `POST /sessions/<name>/turns` with JSON `{"request_id":"job-1","prompt":"Your instruction","provider":"claude"}`; the response is 202 while queued or running. Turn admission submits the turn to the SDK's session log, then commits the stable UUID and watchdog before starting the resident pump through `waitUntil`. The pump reads the oldest unfinished turn, opens or reuses the runtime for its descriptor, commits the background marker before it drives a queued turn, asks the inbox to drive one turn and to settle, and schedules alarms; a turn whose cancellation was requested blocks the session's effects until the drive returns, keyed by its request ID, so a cancel reply that arrives after the drive returned cannot block the next turn. While a session has no bound provider, executor or session ID, admissions run one at a time, so of two concurrent first turns with different providers or executors the later gets 409 as it would sequentially. The pump and `warm` judge a `pending` read against the admission count taken before it, so a read answered after a later admission never marks the queue empty and the order in which WASM command replies arrive does not matter. A pump that fails drops and disposes only the runtime it was using; one that fails before it has a runtime leaves the resident runtime and its background work running. Alarms remain the independent recovery driver. The normal path reuses the already committed watchdog; recovery recommits an existing marker, or one for a running turn, before SDK initialization. Committing the marker in the pump with the descriptor it compares against, instead of at admission with differently ordered keys that the pump then rewrote, saved one statement and one row written per turn: in two alternating `measure-store.mjs` runs on 2026-10-19 against the bundle built before, the object wrote 29.4 instead of 30.4 rows per Claude turn and 80 instead of 81 per Codex turn, with workerd CPU per turn of 12.0 against 11.8 ms and 22.0–23.0 against 21.0–23.0 ms. `Accept: text/event-stream` on the owner turn POST returns a finite, request-scoped durable stream through its terminal result. Hot-path writes do not wait for storage confirmation one at a time. Model dispatch, model socket frames, and executor and hand frames each await `storage.sync()` first, so every earlier write, including SDK receipts, checkpoints and the admitted job, is durable before that effect leaves the session. A tool call one hand's script forwards to another hand, and its result returning to that script, skip the wait: they carry only the hands' own input and output, and the brain keeps no receipt for them. Responses are held by Durable Object output gates until earlier writes are confirmed, so a turn pays one confirmation wait before its first model request instead of one per write. Since the SDK's row store (nanocode-ts AGENTS.md, its 2026-11-04 rows entry) events are published to watchers as they arrive and written to the log at the next tool call, steer, end of turn or settle, so after a reset a client may hold events the log no longer has, and the log continues 16,384 above the highest stored `seq`. In production that single wait averaged 42 ms for Claude and 52 ms for Codex turns, replacing an admission sync, a running-state sync and a sync per checkpoint and event batch before the first dispatch.

Durable Objects bill wall-clock time while an object is handling work or holding a non-hibernatable WebSocket, and SQLite bills every written row including each index entry. Keep both off idle sessions and out of the per-event path. An event-stream response keeps the session object active and billed for as long as it is open, because the object writes to it. The session socket is accepted through the hibernation API, so an idle connected client costs nothing and the object is evicted as if none were attached; prefer it for clients that stay connected. Each watcher's authority is a row in `watch_sockets` and its cursor is in the socket attachment, so events reach watchers after the object is restored. Events are one row each in the SDK's `events` table with `seq` as the plain integer primary key: no secondary index and no `AUTOINCREMENT` counter, and sessions created before that keep their table but drop its indexes. A turn's stream reads its own `first_seq`..`last_seq` range from the SDK's `turns` table, so per-turn reads scan only that primary key range. The SDK hands each logged batch to the session, which pushes it to every socket watcher whose cursor it continues and serves event streams from a tail of up to `EVENT_PAGE_SIZE` recent contiguous events holding at most `EVENT_TAIL_BYTES` of encoded events; a watcher or stream further behind pages through the SDK log. Hands are machines that dial a session so its scripts can use them, such as the laptop where a prompt was typed. A hand is the whole machine under a name, not a workspace: `nanocode hand wss://<host>/sessions/<name>/hands` with the access token in `NANOCODE_RUNNER_TOKEN` attaches the calling machine under its host name, and `--name` or a final `/hands/<name>` path segment names it otherwise. Every session accepts hands. The socket terminates in the session Durable Object through the WebSocket Hibernation API, so an idle attached hand does not keep the object in memory or billed: each hand's registration and tool catalog are stored in `hand_sockets`, the socket carries its connection ID as an attachment, and a woken object rebuilds its hands from the open sockets before handling anything. Hands' heartbeat pings are WebSocket control frames that the runtime answers without waking the object. `GET /sessions/<name>/hands` lists attached names. A turn's `"hand"` names the machine its Code Mode scripts, and those of the subagents it starts, run on; without it scripts run on the session's configured executor, or on the only attached hand when there is no executor, and otherwise fail and list the attached hands. Inside a script any tool call runs on another attached hand when its arguments include `hand: "<name>"` (freeform tools take `{ input, hand }`), so one script can fan out across machines with `Promise.all` or read on one hand and write on another; the call travels from the script's hand through the session to the target and back, and `tools.hands()` lists the attached hands and the script's own. Selecting a hand writes the session's in-memory executor registry, so no discovery, egress lookup or connection setup sits between admission and execution. Hands attach, reconnect and leave at any time: a reconnecting hand replaces its previous socket, and a different hand process attaching under a name already attached, which its catalog's runtime ID tells apart, replaces it too and closes the older one with 1008 and the SDK's `HAND_REPLACED` reason, on which `nanocode hand` stops instead of reconnecting, so two hands started under one name no longer displace each other in a loop, killing each other's cells; the session cannot tell a live older hand from a half-open socket left by a crashed machine, so the newest hand wins; a hand whose name the session cannot use, since names are 1 to 48 lowercase letters, digits, `_` or `-` while `nanocode hand --name` also accepts capitals and longer names, is closed with 1008 and that rule as its reason, which `nanocode hand` prints before it retries, instead of an unexplained close it retried every few seconds; a turn whose hand is absent gets failed cells that dispatched nothing; a call to a hand that is not attached fails without running, so `Promise.allSettled` keeps the other hands' results; and a hand lost mid-call reports an unknown outcome without replay. Nothing waits for a hand: a client attaches its hand before prompting, normally once for its whole session, and submits as soon as the hand is listed. The hand listing includes only hands whose connection the resident SDK can use. A scope opens its runtime in Code Mode on a machine while it has a configured executor, an attached hand or a turn naming a hand. Otherwise it opens in Code Mode without a machine (`createNanocode`'s default; `codeMode: { fetch }` gives scripts a network, `codeMode: false` turns it off): the SDK's Code Mode engine (QuickJS compiled into nanocode-ts's module, `LocalCells`) runs each `exec` cell inside the session object's own isolate, with no network of its own, and the cell's `fetch` is `fetch(authority, env)`'s, so a host can hand it a paying or allowlisted fetch; without `fetch` scripts get no network, which keeps the public demo from serving as an open proxy. Codex model calls within a turn, and across turns queued behind it, share one Responses WebSocket. The WASM host transport asks the session Durable Object to open it; the session checks the request's authority and upgrades through egress `/socket` without waiting for storage, because the handshake carries no session state; the durability wait happens before each frame. The session repeats that durability wait and authority check before every frame it sends. After the first call the SDK sends only new input with `previous_response_id`; a replaced socket or a restored session replays the full history. A non-101 handshake uses the safe Codex error projection: 426 moves the resident session to HTTPS at once, and other retryable rejections fall back after the SDK's retry budget. A socket closed upstream between calls is replaced before the next send. An open outbound socket keeps the session Durable Object in memory and billed, and upstream keeps an idle one for about 15 minutes, so when the session has no queued or running turn and no background work it waits `MODEL_SOCKET_LINGER_MS` and then, if it is still idle, closes its model sockets and disposes a runtime whose configured executor connection would otherwise stay open. It arms that timer only while a resident runtime holds an open model socket (the package's `connected`) or a configured executor connection, or after `warm`: a pending timer keeps the object idle but not hibernateable, which Cloudflare bills for duration (https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), and before 2026-10-20 every Claude turn and every Codex turn over HTTPS armed it with nothing to release, so each burst of turns kept its session billed for the whole linger. `node scripts/measure-idle.mjs [--turns 3] [--linger 30000] [--recovery 30000]` runs Claude and HTTPS Codex turns with production timer policies and reports the timers still pending once each turn's pump has finished, which the local shim tracks with `ctx.waitUntil` promises; on 2026-10-20 against the bundle built before, a 29,998 ms timer was pending after every turn, 3.75 GB-s of billed idle time at 128 MB, and none after the change. A turn admitted within the linger reuses the open socket and sends only its new input; one admitted later opens a new socket and replays the full history. The linger is the operator's price for that latency: 30 s keeps the object billed for at most 30 s × 128 MB = 3.75 GB-s after each burst of turns. Local measurements set it to 0. `warm` on the session socket asks the scope's resident runtime, restored from the last turn's descriptor when needed, to open its Responses socket and then starts the linger, so a client that sends it when the user starts typing moves the handshake and the runtime restore off the next turn, which reuses that socket if it arrives within the linger. While a turn is queued or running or background work is pending, `warm` uses the resident runtime as it is, because reopening it in another hands mode, after a hand attached mid-turn, stopped the running turn and repeated its model call; an idle session's `warm` reopens the runtime in the mode the next turn needs. A Claude runtime has no model socket, so `warm` only restores it. The resident runtime itself costs nothing while idle and is reused if the object stays in memory.

WASM linear memory never shrinks, and allocator fragmentation grows it well past the data it holds: a local 60-turn Claude session with a 4 MB conversation held 12.5 MB live between turns and 28 MB at its peak, while its linear memory reached 44 to 50 MB across runs. Several session objects can share one isolate and its 128 MB limit, so when a session goes idle with linear memory above `RUNTIME_MEMORY_BUDGET_BYTES` (64 MiB, half that limit) it disposes the runtime at once instead of lingering, and the next turn opens a fresh instance from storage. Retiring also drops the session's own reference to that instance: before 2026-10-19 it stayed in the map of reader instances until the next request replaced it, so a retired runtime's linear memory stayed allocated while the object idled. Reopening a 4 MB session took about 120 ms locally; with a 20 MiB budget every turn after the 28th reopened and all 60 completed. Session metrics count these as `runtime_retirements`.

Request results retain observed admission, runtime-open, execution and checkpoint timings. Session metrics expose the resident runtime after completion, aggregate host/WASM/bridge timings and the most recent 64 model dispatches, using the existing diagnostic retention policy. Each dispatch includes a runtime ID, dispatch ID, relative start time, header and body timings, byte counts and the egress's diagnostics, including both attempts after a 401; a Codex socket is one entry with `transport: "websocket"` and send and frame counts. SDK display events expose elapsed model-call time; event envelopes identify their host runtime and receive time. SSE adds `streamed_at` at enqueue time, before any platform output gate or network delivery. No tracing RPCs or additional durability barriers are introduced.

Elapsed times use local clocks; never subtract monotonic timestamps from different runtimes or isolates. Production Worker clocks advance only after I/O, so synchronous WASM, parsing and copy timings can be zero despite consuming CPU. Use a local V8 CPU profile for CPU attribution and keep it separate from production network measurements. Aggregate spans overlap and include the resident SDK task tree; a host operation completing during a turn may have started earlier. Turn timing records are observational and can restart at a recovery boundary. A fresh session does not prove a cold isolate, and an enqueue timestamp does not establish when the client received text.

A new session object starts in a new isolate, and the start time follows the size of this Worker's bundle, not placement or the constructor. Measured from gak-9 (CMH) on 2026-11-14 with scratch Workers whose Durable Object returns at once, a new `idFromName` object then the same object again, 8 rounds each: no modules 100 to 177 ms (again 15 to 50 ms); nanocode_wasm, psh and interpreter (20,000 KiB) 316 to 496 ms; those plus python.wasm (46,773 KiB, this Worker's set) 599 to 1,013 ms. `newUniqueId` took 75 to 92 ms, a constructor with three `CREATE TABLE` statements added 50 to 90 ms on a new object, and `locationHint` (enam, wnam, weur) did not shorten the start (445 to 1,234 ms with the full set). Two copies of this Worker (`nanocode-coldtest-a`, as deployed, 49,366 KiB; `-b`, without `workspace.pythonModule`, 22,587 KiB; containers left out of both), lanes interleaved, a new session per round, 3 turns: Durable Object start (`session_response` minus `session`) on the cold turn, p50/p99, Claude 830/1,463 against 648/1,281 ms (n=12) and 911/1,434 against 628/1,342 ms (n=12), Responses 928/1,349 against 660/931 ms (n=12) and 885/1,554 against 673/1,451 ms (n=10); POST to headers 1,253 against 1,005 ms (Claude) and 1,221 against 1,004 ms (Responses) p50. Without `python.wasm` in this Worker, `python3` would run on the Pyodide object only, without psh `subprocess`, so the module stays until that trade is decided. The web client already names its next session and posts `/warm` while the visitor types (`Transport.warm`), which starts the object before the first turn.

Before this bump (957ff93's predecessor fbc9a2b, `p99.mjs` 12 rounds of 3 turns from gak-9): cold POST to headers p50/p99 Claude 1,045/2,465, Responses 1,024/2,373; POST to first delta Claude 2,616/5,404, Responses 3,063/4,171; Durable Object start 833/1,561 and 844/1,760. `npm run build` passes.

## 2026-11-14: isolate start by bundled module

Each WebAssembly module in this Worker's bundle adds to the start of a new session object, and neither `wasm-opt -Oz` nor a dynamic `import()` lowers it. Module sizes at build-2aad477: nanocode_wasm 13,031,915 bytes (code 11.46 MB, data 1.54 MB), psh 6,226,982 (5.34, 0.87), interpreter 1,213,480 (1.11, 0.10), python.wasm 27,421,795 (code 10.70, baked data 16.69 MB); none has custom or debug sections, so stripping removes nothing. `wasm-opt -Oz` over the released `-O3` modules shrinks nanocode_wasm to 12,713,690 (-2.4%), psh to 6,052,167 (-2.8%) and interpreter to 1,098,092 (-9.5%). Scratch Workers `nanocode-worker-bundle-*` (one Durable Object class that imports the modules and answers `fetch`, deleted after), lanes interleaved per round, a new object per round, Durable Object start measured in the routing Worker from gak-9, p50/p99:

A warm object answered in 18 to 24 ms p50 in every lane. The dynamic `import("./python.wasm")` resolved in 0 ms on a started object, so the runtime compiles every bundled module at isolate start whether it is imported statically or not, and lazy instantiation in the session saves no start time. `-Oz` is within noise, so the release keeps `-O3`. python.wasm costs 145 to 165 ms p50 and 230 to 380 ms p99 of every new session object, about a third of it from its baked data (the stdlib imports the bake saves on the first `python3`). The only change that removes that cost keeps RustPython out of this Worker: RustPython behind the `nanocode-python` Worker would pay a Durable Object call per `python3` (18 to 24 ms p50 warm, 30 to 60 ms p99, plus the mirror of cwd and /tmp), that Worker's own start on an account's first call, and psh `subprocess` and files outside the mirrored roots would need the remote protocol to carry them; local RustPython answers a first `print(1)` in 85 to 113 ms and later ones in 4 to 6.5 ms. Dropping `workspace.pythonModule` alone is not that change: `python3` would then run every script on the Pyodide object (3.5 to 4.0 s wall for a cold `print(1)`) without RustPython being turned off explicitly (`module: false`), so the module stays until the remote RustPython exists.

## 2026-11-14: session pool

`worker/index.ts` exports nanocode-ts's `SessionPool` and binds it as `SESSION_POOL` (migration `v9`, `new_sqlite_classes: ["SessionPool"]`), with `SESSION_POOL_SIZE` 4, `SESSION_POOL_KEEPALIVE_MS` 30000 and `SESSION_POOL_CACHED_NAMES` 10000. The routing Worker binds a new session name to an object that the pool already started (nanocode-ts 566c935), so a new session skips the cold object start. The pin stays at build-eade227, which contains 566c935 and d6d0578 (the routing Worker's provider prime and the session object's `server-timing`, with `session_resolve`). `scripts/seal-pool.mjs <worker name>` imports the ids of the existing `AgentSession` objects into the pool through a temporary `<worker name>-seal` Worker, so that the pool never hands out the object of an existing session, then deletes that Worker.
