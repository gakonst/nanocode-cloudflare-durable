How It Works

nanocode on Cloudflare runs a nanocode agent in a Cloudflare Durable Object. The agent keeps its journal in the object's own SQLite, so a turn that loses its object continues in the next one from the last checkpoint.

Overview

A request reaches the Worker, which forwards it to one Durable Object per account and session. The object runs the nanocode SDK compiled to WebAssembly from nanocode-ts, and its model requests go to Cloudflare AI Gateway through the AI binding.

Before a turn runs, the object stores a watchdog alarm. If the object resets mid-turn, the alarm starts it again, and the turn resumes from the checkpoint in SQLite.

browser ─POST─▶ Worker ─fetch─▶ session Durable Object ─▶ AI Gateway
                                     │
                                     │ checkpoints, turns, events
                                     ▼
                             the object's SQLite
                                     ▲
                                     │ alarm after a reset
                           session Durable Object ─▶ resumes the turn

To try it, open the home page with the deployment's access token, press "Kill the next tool call", then ask for a charge. The object resets during the charge, its alarm starts it again, and the agent reports that the charge may have gone through.

The Agent

createNanocode returns the session Durable Object class and the Worker's fetch handler. The deployment passes its authentication, its model egress, its host tools and the crash route.

worker/index.ts
// One session object per account and session name
const nanocode = createNanocode<Env>({
  authenticate,
  egress: env => aiGateway(() => env.AI.gateway(env.AI_GATEWAY_ID)),
  tools: charge,
  chaos: true,
})

export const { AgentSession } = nanocode
export default { fetch: nanocode.fetch }

The Journal

nanocode keeps its state in SQLite through the SqlHost interface of nanocode-ts. DurableObjectSql from nanocode-ts/cloudflare runs each operation's statements in one transactionSync, so every checkpoint, turn and event is durable when the call returns.

nanocode-ts/src/cloudflare/index.ts
// 1. Run every statement of the operation in one transaction
return this.storage.transactionSync(() =>
  statements.map(([query, ...values]) => {
    const cursor = this.storage.sql.exec(query, ...values)
    // 2. Return the rows to nanocode as arrays
    return [...cursor.raw()]
  }))

The object's SQLite refuses a value above 8 MiB, so the adapter passes that limit to nanocode. nanocode then replaces an oversized event with a marker instead of failing the turn.

Turns and Tools

  • Turns: A turn is a row in nanocode's turn inbox, keyed by its request id. A second request with the same id and prompt returns the same turn.
  • Tools: Before a host tool runs, the object waits for its storage to sync, so the tool's receipt is durable. After a reset, nanocode reports an interrupted call to the model as an unknown outcome.
  • Models: The egress sends nanocode's requests to AI Gateway, which holds the provider credential. The Worker sends none.
  • Events: nanocode logs every event in SQLite. A client streams them as server-sent events and resumes after the last event id it read.

Limits

  • Access: Every request to the Worker needs the deployment's access token. The pages are static assets that need none.
  • Recovery delay: A reset turn resumes when its alarm fires, at most RECOVERY_DELAY_MS after the reset, 5 s in this deployment.
  • Steering: A message sent during a turn becomes the next turn.
