# Development and deployment

This repository is nanocode-cloudflare-durable (gakonst/nanocode-cloudflare-durable, formerly nanocode-worker): nanocode agents running in Durable Objects: a default deployment and demo of nanocode-ts's `nanocode-ts/cloudflare`, which holds the runtime this repository used to (`src/` moved there), the Cloudflare counterpart of gakonst/nanocode-vercel-durable. gakonst/nanocode-ts supplies the agent runtime, the Rust SDK compiled into one WebAssembly module with its host-agnostic TypeScript host and its Cloudflare adapter, as the release tarball `https://github.com/gakonst/nanocode-ts/releases/download/build-<short commit>/nanocode-ts-<short commit>.tgz`, which nanocode-ts's CI builds from each commit on its main and `package-lock.json` pins with its integrity. The tarball carries the compiled JavaScript and module, so this repository builds no Rust: after merging a change there, wait for its `build-<short commit>` release and move the URL with `npm install <tarball URL>`, and read the SDK revision it builds against in its `sdk-revision.json`. Keep SDK changes in the SDK, host-agnostic bridge changes and generic Durable Object plumbing in nanocode-ts and Cloudflare business logic here. The `../nanocode-worker` path is a symlink to this checkout for consumers that still name it. Hosted platform pieces (private egress with credential storage, the vault, execution-host fleets, identity and connectors) live in gakonst/nanocode-platform, which consumes this library.

## Rules

These rules come from gakonst/nanocode's `AGENTS.md` and apply to every change here.

- Do not add code comments, doc comments, or comment headers. Names, types, and this file carry what a reader needs. Only comments that a tool reads stay.
- Do not add tests, test files, or test-only dependencies. Validate a change with `npm run build` (which type-checks), `npm run dry-run`, the local workerd measurements below (`node scripts/measure-*.mjs`, `npm run drill`), and turns against the deployed demo, and record the commands and results here.
- Do not create or edit README files. Development guidance belongs in this file.
- Keep logs, traces, reports, bundles for review, and scratch files in ignored `output/`. Never commit credentials or personal test data.
- Record what a change establishes in this file: the behavior, the reason the code cannot show, and the commands, inputs, dates, and before and after measurements. Correct or remove the entries that the change makes stale, so this file stays a description of the current deployment.
- This repository holds no Rust: do not add Cargo features or wasm-bindgen glue. SDK changes belong in gakonst/nanocode, and host-agnostic bridge and Durable Object changes in gakonst/nanocode-ts.
- Prefer simple code and small changes. Preserve unrelated work.
- Take every limit from a real platform or protocol constraint, a measured requirement, or explicit operator policy, and record its source here. Surface invalid states instead of hiding them with silent truncation, clamping, or fallback values.
- Benchmark performance changes with reproducible commands and inputs, and report before and after results.
- Keep the development loop fast: build only what changed, reuse caches, and skip redundant checks. Honor requests to skip builds or CI.
- Work in the main checkout on `main` and push each completed change to `main`. Do not create worktrees or feature branches. Commit only your own changes, leave other dirty or untracked files alone, and rebase onto `origin/main` when a push is rejected.

Since nanocode-ts e489230 (2026-10-28) the package exports namespaces, so the names below map as `createNanocode` to `App.create`, `aiGateway(ai, id, tier, ms)` to `Gateway.create(ai, { id, serviceTier, firstByteMs })`, `relay` to `Relay.route(request, { namespace })`, `client` to `Limit.client`, `bearerToken` to `Remote.bearerToken` (`nanocode-ts`), `createWallets` to `Wallets.create`, `MachinesEnv` to `Env.Env` (`nanocode-ts/machines/cloudflare`), `visitor` and `VISITOR` to `Account.visitor` and `Account.visitorHeader` (`nanocode-ts/machines/server`), and in the UI `createConfig` to `Config.create`, `modelItems`/`thinkingItems` to `Pickers.models`/`Pickers.thinking`, `cloudflare(...)` to `Transport.create(...)` and `Keyring.keyring` to `Keyring.create`. `worker/index.ts` also passes `mcp.store: env => Listings.store(env.MCP_LISTINGS)`, one `McpListings` Durable Object (migration `v7`) that keeps the Tempo MCP servers' `initialize` and `tools/list` answers for every session: new sessions land in other isolates, whose in-memory listing cache was empty, so on 2026-10-28 a new session's first turn spent 3.1-3.2 s opening its runtime without a warm (two sessions, before) and 60-171 ms after the first session of the deployment had stored the listings (that first one 4.3 s). `createNanocode(options)` from `nanocode-ts/cloudflare` (nanocode-ts's `src/cloudflare/App.ts`), which returns the `AgentSession` Durable Object class and the Worker `fetch` handler. The library defines interfaces and ships no adapters. `options.authenticate(request, env)` returns the caller's account ID, `{account, read_only: true}` for a caller that may only read, or `null`; each account's sessions live in separate objects named by `[account, session]`. A read-only caller gets 403 for every session request other than GET and for attaching a hand, and its session socket streams events but answers `turn` and `cancel` with 403 and `warm` with `warmed: false`. A principal may also carry `grant`, a JSON value the host defines, and `expires_at`, its credential's expiry in milliseconds since the epoch. The session keeps both with each turn the caller submits, with its session socket's registration and with its hand's `hand_sockets` row, and passes the grant of the turn it is running to host tool calls. Sockets and event streams outlive the request that authenticated them, so the session checks the caller before it admits each session socket message, before it delivers events to a watcher, before each read of an event stream and before each frame it sends to a hand or accepts from one, in arrival order: past `expires_at`, or when the optional `options.active(account, grant, env)` returns false or throws, it sends the session socket `{"type":"error","error":"access token expired or revoked"}` and closes it with 1008, ends the event stream, or disposes the hand connection, which fails the cell that was being sent as not dispatched and detaches the hand. Event delivery runs the `active` check in the background, so a watcher can receive the batch published while its first failing check runs; hosts that cache the answer bound how long a revocation takes beyond that. The error frame arrives at once, but a close issued outside the socket's own message handler reached the client about 10 s later in local workerd and 42 s later in production, while one issued from its message handler arrived within 319 ms in production. `options.egress(env)` returns anything with `fetch(request)` that answers the egress contract: `POST /model` with the provider body and the `x-nanocode-model` JSON header `{provider, authority, endpoint, headers, subscription}`, `GET /socket` upgrades for Codex Responses sockets with `x-nanocode-socket`, `GET /remote` upgrades to a configured execution host with `x-nanocode-authority`, and `GET /metrics`. A service binding to a separate Worker satisfies it directly. `MODEL_AUTH` tells the agent whether both providers use subscription or API-key wire compatibility; the optional `options.subscription(account, env, provider)` decides it per account and provider instead, for an egress that holds each account's own credentials. The optional `options.recordSession(account, name, env)` lets a host keep an index of each account's sessions: a session object calls it before handling its first request and, once it returns true, writes a `recorded` metadata row and never calls it again, so sessions created earlier are indexed on their next request; false means the account no longer exists, and the session deletes its storage and answers 403. The returned `deleteSession(account, name, env)` calls the session object's internal delete route, which the public routes cannot reach: it closes the session's hand and watcher sockets, disposes its runtimes and their model sockets, deletes its alarm and all of its storage, and the instance answers 410 until it is evicted and opens no WASM instance meanwhile, since the recovery note of a turn that was running when the session was deleted recreated the turn log's tables in the emptied storage. Claude subscription sessions use Claude Code's wire compatibility. Codex subscription sessions use the ChatGPT Responses WebSocket with `OpenAiAuth::host_managed_chatgpt()`, and Codex API-key sessions use the public Responses API at `https://api.openai.com/v1` over HTTPS with `OpenAiAuth::gateway_managed()` and the SDK's default of store: false, so every model call replays the full history and OpenAI retains nothing; Codex subscription sessions also keep store: false, as the ChatGPT backend requires, and continue responses on their socket. The SDK can store and continue API-key responses with `.store(true)`, but measured through AI Gateway storing a response delayed its first byte by about 0.2 s while continuing one saved only request bytes, so the Worker leaves it off. The egress must agree, and a resident runtime reopens when a later turn's mode differs. The library makes no outbound requests itself and holds no credentials.

Binding requests are pre-authenticated, so the Worker holds no provider key or gateway token. The WASM agent and SQLite checkpoints run inside the same session Durable Object. A stable session UUID is persisted before SDK initialization. Turns are queued durably in the SDK's turn inbox and deduplicated by `request_id`; reusing an ID with different input returns 409. SDK ownership fences, revision checks, immutable records, model receipts, tool receipts, subagent journals, and checkpoints use the persistent store. No memory store is used for agent state.

Alarms drive work independently of client connections. A watchdog alarm is persisted before execution, using `RECOVERY_DELAY_MS` as an operator recovery policy. Completed requests return saved results. Interrupted model calls may repeat; dispatched tools retain the SDK's uncertain-outcome handling. The Worker does not promise exactly-once model billing or external side effects. Concurrent sessions use independent Durable Objects. Each session executes queued root turns serially, while SDK subagents can run concurrently. Durable background markers keep alarms armed after root requests finish until the SDK task tree, continuation turns, journal writes, and detached remote execution are quiescent. Resume pending SDK operations in accepted order before later requests. Cancellation must settle in the SDK before the queue reports it complete, except for a turn whose runtime cannot open, which finishes cancelled at once and which the SDK cancels on admission when the runtime next opens, and a turn whose cancellation was requested when its drive fails, which finishes cancelled the same way: a turn whose drive fails every time, such as one whose events could not be logged before the SDK replaced oversized ones, otherwise recovered every `RECOVERY_DELAY_MS` forever while every later turn stayed queued, and cancelling it changed nothing. The SDK reserves the `subagent-completion:` request-ID prefix for its own continuation turns, and admission answers 400 for it.

A turn waits instead of running while its execution host is unavailable: when the runtime for it cannot open, or it names a `hand` that is not attached, the pump classifies the failure from its signal and does not guess. Permanent failures finish the turn as failed with `error` and `kind` in its result, so a client's wait ends: a non-101 answer from egress `/remote` with a 4xx status other than 408 and 429, which is `unauthorized` for 401 and 403 and `rejected` otherwise, a 501 (`rejected`), and a runtime configuration the SDK refuses while building it (`configuration`, which `init` answers as a rejection). Everything else is transient and keeps the turn queued, or running for a recovered turn, under `RECOVERY_DELAY_MS`: a 5xx other than 501, 408 or 429 from `/remote` (`unavailable`), no HTTP answer, the `REMOTE_TIMEOUT_MS` connection deadline or a socket closed before its catalog (`unreachable`), an absent hand (`detached`) and any other open failure (`runtime`). The SDK session log's `retry` keeps the message, kind, attempt count and next retry time on the turn, its status report shows them as `error`, `kind`, `attempts` and `retry_at`, and its event stream gets a `retrying` event when the error first appears or changes, not on every retry. A hand attaching starts a turn waiting for it at once. Cancelling a waiting turn finishes it, and session metrics report the pending alarm as `alarm_at`, `null` once nothing is left to retry. The pump commits the background marker only once a queued turn's runtime has opened, so a turn whose runtime never opened leaves nothing retrying after it fails or is cancelled; with no unfinished turn, a permanent failure drops an existing marker and a transient one keeps retrying for the SDK's background work.

Cloudflare chooses physical Durable Object placement. Agent execution and checkpoint storage are co-located by construction; this does not pin all objects to an exact Cloudflare colo. SQLite access stays inside each session, including the full SDK subagent tree. Reuse the resident WASM instance and SDK session across turns. Status, a queued turn's cancellation and event history read through the SDK's session log on a WASM instance without opening the SDK session (instantiating the compiled module took 0.3 ms locally), and opening the session later reuses that instance. Root turns are serial, while SDK children can run concurrently.

The default tool collection omits local machine tools and enables SDK delegation. Shell, filesystem, desktop, and remote Code Mode execution require a separately configured execution host; this Worker does not create a machine environment: hands dial in, and an egress may connect configured execution hosts at `/remote`. Use the SDK RemoteFrame/RemoteOperation protocol for that host, with orchestration and tool receipts remaining in the brain. A machine executor's unrestricted network access is governed by that host; the Worker cannot enforce a proxy for an independently configured machine.

Recovery delay, event page size, the event tail's byte bound, event coalescing, the event-stream keepalive interval (`EVENT_STREAM_KEEPALIVE_MS`), the model-socket linger, the runtime memory budget, and execution-host frame and timeout policies are explicit Wrangler variables.

The package's `AgentRuntime`, `EventHub` and `RemoteExecutor`, its bridge ABI and command table are documented in nanocode-ts's `AGENTS.md`; protocol, turn and event logic belongs in the SDK and host-agnostic glue in the package. The session Durable Object supplies the package's host interfaces. nanocode-ts's `src/cloudflare/internal/Checkpoints.ts` is its `SqlHost`, the package's `Sql.create` (`nanocode-ts/cloudflare`) with the Worker's metrics as its observer: it runs each `store` or `log` operation's statements in one `transactionSync` and answers with each statement's rows; metrics count the two separately (`checkpoints` and `log`). The SDK owns the `states`, `owners`, `records`, `turns` and `events` tables, their fencing, revisions and record immutability, turn states and event sequence; the Worker only reads their row counts for metrics. Model requests go to egress `/model`; Codex Responses sockets upgrade through egress `/socket`, and the session accepts the WebSocket and hands it to the package with the egress's `x-nanocode-stream-idle-ms` deadline. nanocode-ts's `src/cloudflare/internal/Executor.ts` dials a configured execution host through egress `/remote` with `Remote.connect` and throws `Executor.RejectedError` with the status of a refused upgrade, and hands attach through the hibernation API with `RemoteExecutor.accept` and `restore`, so frames stay opaque, `REMOTE_MAX_FRAME_BYTES` is enforced and each hand's catalog text is kept for hibernation. The package flags each batch that holds a request the SDK's `RemoteFrame::dispatches` marks as starting work, so the session refuses that batch once the turn's cancellation is requested without decoding frames. Two commands run on the scope's WASM instance without opening the SDK session: `catalog` reads the name a hand advertises in its catalog, and `admit` asks the SDK's `admit_prompt` whether a turn may enter the inbox, so admission takes the reserved request-ID prefix and the provider rule from the SDK. Each logged event batch reaches the session's `published` callback with `host_timing`, the session answers a finished turn's timings through `finishing`, and the SDK selects each turn's hand with `select_prompt_hand`; turn states, the queue, cancellation before and during a turn, resumption in accepted order, event attribution and quiescence live in the SDK. Egress injects provider credentials, so Claude clients send no auth headers and Codex uses `OpenAiAuth::host_managed_chatgpt()`.

Hosts add their own tools through `createNanocode({ tools: { definitions, call } })`. `createNanocode({ streamToolInput: true })`, which the default deployment sets, opens sessions with nanocode-ts's `stream_tool_input`, so the event stream also carries each tool call's input while the model writes it, and the page's shared `Transcript` shows the call, such as a `charge` with its memo, as a live line until it starts. Each definition's `name`, `description` and JSON Schema `parameters` reach the runtime when it opens, and the package registers them as the SDK's `FunctionTool`s beside the SDK's own tools, offered directly or inside Code Mode scripts. A call crosses the bridge as the `tool_call` host operation; the session Durable Object takes the durability wait it takes before any external effect, refuses it once the turn's cancellation is requested, and awaits `call({ authority, name, input, grant }, env, signal)`, whose result becomes the tool output and whose thrown error a tool error. `grant` is the grant of the turn the session is running, read from its `background:<scope>` row, which holds that turn's descriptor until the runtime settles, so subagents and other background work that continue after a turn run with the grant of the latest turn the session started, and turns submitted before grants existed carry none. The SDK keeps the call's receipt like any tool's, so an interrupted call reports an unknown outcome instead of running again, and session metrics count `host_tool_calls`. Whatever the host keeps out of the result never enters WASM memory, checkpoints or events; the platform serves its credential tools this way so injected secrets stay in its egress.

Deploy from this directory:

1. Run `npx wrangler login`, or provide `CLOUDFLARE_API_TOKEN` through your secret manager.
2. In AI Gateway, use the `default` gateway or create one and set `AI_GATEWAY_ID`. Add an Anthropic key under Provider Keys with the `default` alias, or load Unified Billing credits; the AI binding consults only the `default` alias.
3. Generate an access token, keep it in your secret manager, and deploy with its digest: `npx wrangler deploy --var ACCESS_TOKEN_SHA256:$(printf %s "$TOKEN" | shasum -a 256 | cut -d' ' -f1)`. Clients and hands send the token itself as `Authorization: Bearer`.
4. `npm run dry-run` bundles the Worker and its `public/` assets into `output/deploy` for review. Wrangler adds files to an existing output directory without removing old ones, so bundle into a fresh directory, such as `--outdir output/deploy-ts`, when `output/deploy` holds a bundle from before the nanocode-ts move, and point `NANOCODE_BUNDLE_PATH` at it.

Requests require `Authorization: Bearer <access token>`. Submit `POST /sessions/<name>/turns` with JSON `{"request_id":"job-1","prompt":"Your instruction","provider":"claude"}`; the response is 202 while queued or running. Poll `GET /sessions/<name>/turns/job-1` for the final result; while the turn waits on an unavailable execution host the report adds `error`, `kind`, `attempts` and `retry_at`. `POST /sessions/<name>/warm` with JSON `{"provider","model"}`, which a session that has bound its own ignores, opens the session's WASM instance and calls egress `/warm`, and answers 204, or egress's status when that fails; for a Workers AI model it only opens the instance, because on 2026-10-21 a one-token GLM-5.3 request through the gateway took 25 and 74 s and GLM's first turns took 1.3 to 22 s to their response headers without it. Repeating the POST with the same input returns the saved result after completion. A turn may also name a `model`, which the session's first accepted turn binds like its provider (a different one later answers 409; sessions created before the binding count as bound to the deployment's model), and a reasoning effort `thinking` (`none`, `low`, `medium`, `high`, `xhigh` or `max`, 400 otherwise) that the session object applies with nanocode-ts's `setThinking` (since ddff939) before it drives that turn; an effort the session's model does not take fails the turn with kind `configuration` and the SDK's message. Model diagnostics report each request's `model` and `effort`. A turn POST with `"steer": true` steers the running turn instead of queuing one: the session object hands it to nanocode-ts's `steer` (since e79b665) with the POST's `request_id` as the steer's identity, which the SDK accepts once, and answers 200 `{"status":"steered"}`, or 409 when no turn is running or the running one no longer takes steering, so the client can send it as a turn; the SDK gives a steer to the model at its next call, and the reply to it arrives in the running turn's events. Cancel with `POST /sessions/<name>/turns/job-1/cancel`. Read bounded event pages at `GET /sessions/<name>/events?after=0&limit=128` and process counters at `GET /sessions/<name>/metrics`. Event streams resume after the larger of `after` and the `Last-Event-ID` header that Server-Sent Events clients send when they reconnect, and only `turns` and `hands` take a further path segment, so `/cancel` cancels only under `/turns/<id>`. A turn whose prompt the session log cannot store within the SQLite value limit, counting its input.accepted event, gets 413 with the `bytes` it needs and the `limit`, and a request body above the limit gets 413 before it is read. HEAD on a GET route answers as GET without a body. `GET /sessions/<name>/socket?after=<seq>` upgrades to a hibernating session WebSocket that first sends every stored event after the cursor and then each new one as `{"type":"event","seq","request_id","created_at","event"}`. On it the client sends `{"type":"turn",...}` with the turn body and `{"type":"cancel","request_id"}`, answered by `{"type":"turn"|"cancel","request_id","status","body"}` with the HTTP route's status and body, and `{"type":"warm"}`, answered by `{"type":"warm","warmed"}`. The text message `ping` is answered `pong` by the runtime without waking the session. Reconnect with the last `seq` seen as `after`. `scripts/worker-client.mjs` uses this socket and sends `warm` on the first keypress of each interactive prompt. Omit `provider` for Claude Opus 5.5; `"provider":"codex"` selects GPT-6.1 Sol when the egress serves Codex. Provider selection is durable and immutable within each SDK session: the session records its first turn's provider and the SDK's `admit_prompt` refuses another with 409; choose a new session name to switch providers. The first turn's `executor` binds the session the same way, a rule the Worker keeps itself because the SDK records no executor. `GET /health` reports supported models and the Claude authentication mode; it does not probe provider availability. Subscription requests retain the SDK's pinned wire compatibility. `npm run dev` runs the Worker under Wrangler with the remote AI binding.

Turn admission submits the turn to the SDK's session log, then commits the stable UUID and watchdog before starting the resident pump through `waitUntil`. The pump reads the oldest unfinished turn, opens or reuses the runtime for its descriptor, commits the background marker before it drives a queued turn, asks the inbox to drive one turn and to settle, and schedules alarms; a turn whose cancellation was requested blocks the session's effects until the drive returns, keyed by its request ID, so a cancel reply that arrives after the drive returned cannot block the next turn. While a session has no bound provider, executor or session ID, admissions run one at a time, so of two concurrent first turns with different providers or executors the later gets 409 as it would sequentially. The pump and `warm` judge a `pending` read against the admission count taken before it, so a read answered after a later admission never marks the queue empty and the order in which WASM command replies arrive does not matter. A pump that fails drops and disposes only the runtime it was using; one that fails before it has a runtime leaves the resident runtime and its background work running. Alarms remain the independent recovery driver. The normal path reuses the already committed watchdog; recovery recommits an existing marker, or one for a running turn, before SDK initialization. Hot-path writes do not wait for storage confirmation one at a time. Model dispatch, model socket frames, and executor and hand frames each await `storage.sync()` first, so every earlier write, including SDK receipts, checkpoints and the admitted job, is durable before that effect leaves the session. A tool call one hand's script forwards to another hand, and its result returning to that script, skip the wait: they carry only the hands' own input and output, and the brain keeps no receipt for them. Responses and streamed events are held by Durable Object output gates until earlier writes are confirmed. A turn therefore pays one confirmation wait before its first model request instead of one per write, and a crash before confirmation loses only work that nothing outside the session has observed. In production that single wait averaged 42 ms for Claude and 52 ms for Codex turns, replacing an admission sync, a running-state sync and a sync per checkpoint and event batch before the first dispatch.

Durable Objects bill wall-clock time while an object is handling work or holding a non-hibernatable WebSocket, and SQLite bills every written row including each index entry. Keep both off idle sessions and out of the per-event path. An event-stream response keeps the session object active and billed for as long as it is open, because the object writes to it. The session socket is accepted through the hibernation API, so an idle connected client costs nothing and the object is evicted as if none were attached; prefer it for clients that stay connected. Each watcher's authority is a row in `watch_sockets` and its cursor is in the socket attachment, so events reach watchers after the object is restored. Events are one row each in the SDK's `events` table with `seq` as the plain integer primary key: no secondary index and no `AUTOINCREMENT` counter, and sessions created before that keep their table but drop its indexes. A turn's stream reads its own `first_seq`..`last_seq` range from the SDK's `turns` table, so per-turn reads scan only that primary key range. The SDK hands each logged batch to the session, which pushes it to every socket watcher whose cursor it continues and serves event streams from a tail of up to `EVENT_PAGE_SIZE` recent contiguous events holding at most `EVENT_TAIL_BYTES` of encoded events; a watcher or stream further behind pages through the SDK log. The byte bound is 4 MiB: on 2026-10-20 the 1,840 events of the platform's 60 most recent sessions had a median of 552 bytes, a 99th percentile of 1.8 KB and a maximum of 19 KB, so the tail keeps all 128 events of every measured kind, up to 32 KiB each, while a session's tail stays within a sixteenth of the 64 MiB an isolate has beside `RUNTIME_MEMORY_BUDGET_BYTES`; counted by events alone, 128 events near the 1 MiB hand frame limit kept 134 MB of heap in one session (`scripts/measure-events.ts` in nanocode-ts). The SDK's `SessionEvents` pump sends the first event after a quiet period at once and then at most one batch per `EVENT_COALESCE_MS`, an operator policy for how often a streaming client sees new text (100 ms, ten updates a second), and merges consecutive assistant and reasoning-summary deltas of the same item into one event. Hands are machines that dial a session so its scripts can use them, such as the laptop where a prompt was typed. A hand is the whole machine under a name, not a workspace: `nanocode hand wss://<host>/sessions/<name>/hands` with the access token in `NANOCODE_RUNNER_TOKEN` attaches the calling machine under its host name, and `--name` or a final `/hands/<name>` path segment names it otherwise. Every session accepts hands. The socket terminates in the session Durable Object through the WebSocket Hibernation API, so an idle attached hand does not keep the object in memory or billed: each hand's registration and tool catalog are stored in `hand_sockets`, the socket carries its connection ID as an attachment, and a woken object rebuilds its hands from the open sockets before handling anything. Hands' heartbeat pings are WebSocket control frames that the runtime answers without waking the object. `GET /sessions/<name>/hands` lists attached names. A turn's `"hand"` names the machine its Code Mode scripts, and those of the subagents it starts, run on; without it scripts run on the session's configured executor, or on the only attached hand when there is no executor, and otherwise fail and list the attached hands. Inside a script any tool call runs on another attached hand when its arguments include `hand: "<name>"` (freeform tools take `{ input, hand }`), so one script can fan out across machines with `Promise.all` or read on one hand and write on another; the call travels from the script's hand through the session to the target and back, and `tools.hands()` lists the attached hands and the script's own. Selecting a hand writes the session's in-memory executor registry, so no discovery, egress lookup or connection setup sits between admission and execution. Hands attach, reconnect and leave at any time: a reconnecting hand replaces its previous socket, and a different hand process attaching under a name already attached, which its catalog's runtime ID tells apart, replaces it too and closes the older one with 1008 and the SDK's `HAND_REPLACED` reason, on which `nanocode hand` stops instead of reconnecting, so two hands started under one name no longer displace each other in a loop, killing each other's cells; the session cannot tell a live older hand from a half-open socket left by a crashed machine, so the newest hand wins; a hand whose name the session cannot use, since names are 1 to 48 lowercase letters, digits, `_` or `-` while `nanocode hand --name` also accepts capitals and longer names, is closed with 1008 and that rule as its reason, which `nanocode hand` prints before it retries, instead of an unexplained close it retried every few seconds; a turn whose hand is absent gets failed cells that dispatched nothing; a call to a hand that is not attached fails without running, so `Promise.allSettled` keeps the other hands' results; and a hand lost mid-call reports an unknown outcome without replay. Nothing waits for a hand: a client attaches its hand before prompting, normally once for its whole session, and submits as soon as the hand is listed. The hand listing includes only hands whose connection the resident SDK can use. A scope opens its runtime in Code Mode on a machine while it has a configured executor, an attached hand or a turn naming a hand. Otherwise it opens in Code Mode without a machine (`createNanocode`'s default; `codeMode: { fetch }` gives scripts a network, `codeMode: false` turns it off): the SDK's Code Mode engine (QuickJS compiled into nanocode-ts's module, `LocalCells`) runs each `exec` cell inside the session object's own isolate, with no network of its own, and the cell's `fetch` is `fetch(authority, env)`'s, so a host can hand it a paying or allowlisted fetch; without `fetch` scripts get no network, which keeps the public demo from serving as an open proxy. Host tools are then `tools.<name>()` calls inside scripts, crossing the bridge and the durability wait as before, and cell frames take the same durability wait and authority checks as a hand's. With `codeMode: false` the model gets the SDK's direct tools. `createNanocode({ instructions })` adds host instructions to every session's developer context, such as the services a paying `fetch` reaches. On 2026-10-22 the public demo, then on nanocode-ts build-de5fd83 with a Dynamic Worker per cell, ran one turn each on Claude Haiku 5.5 and Codex Luna whose single `exec` cell computed a sum, called `charge` and caught the offline `fetch`'s refusal, both completing in about 7.3 s with one host tool call. Redeployed the same day with QuickJS cells (nanocode-ts build-ce9f311), the same turns completed in 9.4 s (Haiku) and 6.7 s (Luna). A turn that changes the mode reopens the resident runtime, and hand connections pass to the new runtime, and to a runtime opened after a failure, without reconnecting, so their Code Mode state survives. Hand frames use `REMOTE_MAX_FRAME_BYTES` and `REMOTE_TIMEOUT_MS`. The SDK tells each hand the frame limit, so a script result, nested-call update or cross-hand call above it fails or drops its payload alone instead of closing the hand's socket, and Execute and Wait deadlines add the yield a script asks for to `REMOTE_TIMEOUT_MS`, while a call one hand's script makes on another hand is bounded by `REMOTE_TIMEOUT_MS` alone: a cross-hand command running longer fails as an unknown outcome and keeps running on its hand. The session's own refusals of a frame (a revoked hand, a cancelled turn, a connection that moved to a newer runtime or a failed durability wait) throw the package's `RemoteRefusal` before anything reaches the socket, and dispose a refused hand only after the refusal reaches the SDK, so the cell reports that nothing was dispatched. `scripts/worker-client.mjs --origin <url> --session <name> --hand <name>` submits once the session lists the hand; `-` as the prompt reads one prompt per stdin line and `--timing` reports per-turn connection, acceptance and first-text times.

Codex model calls within a turn, and across turns queued behind it, share one Responses WebSocket. The WASM host transport asks the session Durable Object to open it; the session checks the request's authority and upgrades through egress `/socket` without waiting for storage, because the handshake carries no session state; the durability wait happens before each frame. The session repeats that durability wait and authority check before every frame it sends. After the first call the SDK sends only new input with `previous_response_id`; a replaced socket or a restored session replays the full history. A non-101 handshake uses the safe Codex error projection: 426 moves the resident session to HTTPS at once, and other retryable rejections fall back after the SDK's retry budget. A socket closed upstream between calls is replaced before the next send. An open outbound socket keeps the session Durable Object in memory and billed, and upstream keeps an idle one for about 15 minutes, so when the session has no queued or running turn and no background work it waits `MODEL_SOCKET_LINGER_MS` and then, if it is still idle, closes its model sockets and disposes a runtime whose configured executor connection would otherwise stay open. It arms that timer only while a resident runtime holds an open model socket (the package's `connected`) or a configured executor connection, or after `warm`: a pending timer keeps the object idle but not hibernateable, which Cloudflare bills for duration (https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), and before 2026-10-20 every Claude turn and every Codex turn over HTTPS armed it with nothing to release, so each burst of turns kept its session billed for the whole linger. `node scripts/measure-idle.mjs [--turns 3] [--linger 30000] [--recovery 30000]` runs Claude and HTTPS Codex turns with production timer policies and reports the timers still pending once each turn's pump has finished, which the local shim tracks with `ctx.waitUntil` promises; on 2026-10-20 against the bundle built before, a 29,998 ms timer was pending after every turn, 3.75 GB-s of billed idle time at 128 MB, and none after the change. A turn admitted within the linger reuses the open socket and sends only its new input; one admitted later opens a new socket and replays the full history. The linger is the operator's price for that latency: 30 s keeps the object billed for at most 30 s × 128 MB = 3.75 GB-s after each burst of turns. Local measurements set it to 0. `warm` on the session socket asks the scope's resident runtime, restored from the last turn's descriptor when needed, to open its Responses socket and then starts the linger, so a client that sends it when the user starts typing moves the handshake and the runtime restore off the next turn, which reuses that socket if it arrives within the linger. While a turn is queued or running or background work is pending, `warm` uses the resident runtime as it is, because reopening it in another hands mode, after a hand attached mid-turn, stopped the running turn and repeated its model call; an idle session's `warm` reopens the runtime in the mode the next turn needs. A Claude runtime has no model socket, so `warm` only restores it. The resident runtime itself costs nothing while idle and is reused if the object stays in memory.

WASM linear memory never shrinks, and allocator fragmentation grows it well past the data it holds: a local 60-turn Claude session with a 4 MB conversation held 12.5 MB live between turns and 28 MB at its peak, while its linear memory reached 44 to 50 MB across runs. Several session objects can share one isolate and its 128 MB limit, so when a session goes idle with linear memory above `RUNTIME_MEMORY_BUDGET_BYTES` (64 MiB, half that limit) it disposes the runtime at once instead of lingering, and the next turn opens a fresh instance from storage. Retiring also drops the session's own reference to that instance: before 2026-10-19 it stayed in the map of reader instances until the next request replaced it, so a retired runtime's linear memory stayed allocated while the object idled. Reopening a 4 MB session took about 120 ms locally; with a 20 MiB budget every turn after the 28th reopened and all 60 completed. Session metrics count these as `runtime_retirements`.

Use `node scripts/summarize-timing.mjs output/<report>.json` to inspect a measurement's timing breakdown. Request results retain observed admission, runtime-open, execution and checkpoint timings. Session metrics expose the resident runtime after completion, aggregate host/WASM/bridge timings and the most recent 64 model dispatches, using the existing diagnostic retention policy. Each dispatch includes a runtime ID, dispatch ID, relative start time, header and body timings, byte counts and the egress's diagnostics, including both attempts after a 401; a Codex socket is one entry with `transport: "websocket"` and send and frame counts. SDK display events expose elapsed model-call time; event envelopes identify their host runtime and receive time. SSE adds `streamed_at` at enqueue time, before any platform output gate or network delivery. No tracing RPCs or additional durability barriers are introduced.

Elapsed times use local clocks; never subtract monotonic timestamps from different runtimes or isolates. Production Worker clocks advance only after I/O, so synchronous WASM, parsing and copy timings can be zero despite consuming CPU. Use a local V8 CPU profile for CPU attribution and keep it separate from production network measurements. Aggregate spans overlap and include the resident SDK task tree; a host operation completing during a turn may have started earlier. Turn timing records are observational and can restart at a recovery boundary. A fresh session does not prove a cold isolate, and an enqueue timestamp does not establish when the client received text.
